# بروتوكول إصلاح الكسور (Breaking Changes Fix Protocol)

## 📋 القواعد الأساسية

### 1. **الإصلاح التدريجي (Incremental Fixes)**
- ✅ إصلاح كسر واحد في كل مرة
- ❌ عدم إصلاح عدة كسور دفعة واحدة
- 📝 كل إصلاح = commit منفصل

### 2. **الاختبار الإلزامي (Mandatory Testing)**
- ✅ اختبار كل إصلاح فور تنفيذه
- ✅ التأكد من عدم حصول كسور جديدة
- ✅ اختبار الوظائف المرتبطة
- 📝 توثيق نتائج الاختبار

### 3. **الانتقال المشروط (Conditional Progression)**
- ⏸️ عدم الانتقال للكسر التالي إلا بعد موافقة المستخدم
- ✅ انتظار تأكيد "واصل" أو "التالي"
- 📝 تلخيص ما تم إصلاحه قبل الانتقال

### 4. **المرونة في الترتيب (Flexible Order)**
- ✅ السماح بإصلاح كسر محدد
- ✅ السماح بتجاوز كسور معينة
- ✅ السماح بتغيير الأولويات
- 📝 توثيق الكسور المتجاوزة

### 5. **النسخة المعتمدة (Authoritative Version)**
- 🔙 **النسخة القديمة (master) هي المعتمدة افتراضياً**
- ⚠️ إلا في حالتين:
  1. التغيير ضروري تقنياً للميزات الجديدة
  2. المستخدم يحدد النسخة المعتمدة صراحةً
- 📝 توثيق سبب الاحتفاظ بالنسخة الجديدة

---

## 📐 قواعد إضافية مقترحة

### 6. **التوثيق الإلزامي (Mandatory Documentation)**
- 📝 توثيق كل إصلاح في commit message
- 📝 شرح سبب الإصلاح
- 📝 ذكر الملفات المتأثرة
- 📝 إضافة رقم الكسر من التقرير

**مثال على Commit Message:**
```
fix(breaking-change-1): restore entity_id in PlayerClient API calls

- Restored missing entity_id parameter in handleAddSegment()
- Restored missing entity_id parameter in handleDeleteSegment()
- Restored missing entity_id parameter in updateSegment()
- Reverted from saveEntity() to direct axios calls for online mode
- Added offline fallback using saveEntity()

Fixes: Breaking Change #1 from breaking_changes_report.md
Testing: Manual testing of segment CRUD operations
```

### 8. **التحقق من التبعيات (Dependency Check)**
- 🔍 فحص الملفات التي تستخدم الكود المُصلح
- 🔍 التأكد من عدم كسر ملفات أخرى
- 📝 قائمة بالملفات المتأثرة

**مثال:**
```bash
# البحث عن استخدامات handleAddSegment
git grep "handleAddSegment" --name-only
```

### 9. **الأولوية حسب الخطورة (Priority by Severity)**
- 🔴 **أولوية عالية**: الكسور الحرجة (1-8)
- 🟡 **أولوية متوسطة**: الكسور المتوسطة (9-20)
- 🟢 **أولوية منخفضة**: التحسينات الاختيارية

### 10. **استراتيجية الإصلاح (Fix Strategy)**
لكل كسر، تحديد الاستراتيجية:
- **A. Revert**: الرجوع للنسخة القديمة بالكامل
- **B. Hybrid**: دمج القديم والجديد
- **C. Fix**: إصلاح الجديد مع الاحتفاظ به
- **D. Skip**: تجاوز (بموافقة المستخدم)

### 11. **سجل الإصلاحات (Fix Log)**
- 📝 الاحتفاظ بسجل في ملف `fix-log.md`
- 📝 تحديث السجل بعد كل إصلاح

### 12. **التحقق النهائي (Final Verification)**
بعد كل إصلاح:
- ✅ تشغيل التطبيق 
- تسجيل الدخول باستخدام (admin@admin.com / password) وعمل كترل+a لمسح البريد الالكتروني وكلمة المرور الموجودة في الحقلين 
- اطلب مني الرابط في حال بحثت عنه اكثر من مرتين ولم تصل الى الموقع المطلوب
- ✅ اختبار الوظيفة المُصلحة
- ✅ اختبار الوظائف المرتبطة
- ✅ فحص console للـ errors
- ✅ فحص network tab للـ API calls

## 🔄 سير العمل (Workflow)

### المرحلة 1: التحضير
قراءة الملفات المتعلقة بالاصلاحات من محلد .agent/breaking-changes-report.md و .agent/fix-log.md 

### المرحلة 2: لكل كسر
```
1. قراءة تفاصيل الكسر من التقرير
2. تحديد الاستراتيجية (Revert/Hybrid/Fix/Skip)
3. إنشاء backup للملف (إذا لزم)
4. تنفيذ الإصلاح
5. الاختبار الفوري
6. Commit مع رسالة واضحة
7. تحديث fix-log.md وتكون طريقة التوثيق كالتالي:
نفس المنهجية المتبعة في ملف sync-milestones.md
8. انتظار موافقة المستخدم
9. الانتقال للكسر التالي
```

### المرحلة 3: بعد كل إصلاح
```
1. عرض ملخص الإصلاح
2. عرض نتائج الاختبار
3. طلب موافقة المستخدم
```

## 🎯 نقاط مهمة

### ✅ افعل (Do)
- اتبع القواعد بدقة
- اختبر كل شيء
- وثّق كل شيء
- اسأل عند الشك
- احتفظ بنسخ احتياطية

### ❌ لا تفعل (Don't)
- لا تصلح عدة كسور دفعة واحدة
- لا تتسبب في كسور جديدة عند الاصلاح
- لا تنتقل للتالي بدون موافقة
- لا تفترض النسخة المعتمدة
- لا تتجاوز الاختبار
- لا تنسى التوثيق

```
✅ تم إصلاح الكسر #X: [اسم الكسر]

📝 التفاصيل:
- الملف: [اسم الملف]
- الاستراتيجية: [Revert/Hybrid/Fix]
- التغييرات: [قائمة مختصرة]

🧪 الاختبار:
- [نتيجة الاختبار 1]
- [نتيجة الاختبار 2]

📊 الحالة:
- الكسور المُصلحة: X/20
- الكسور المتبقية: Y/20

❓ هل تريد المتابعة للكسر التالي؟
```

```bash
